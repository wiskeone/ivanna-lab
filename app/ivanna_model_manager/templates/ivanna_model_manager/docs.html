1. Platform overview

Ivanna Lab is a self-hosted LLM model lab: a single web app that covers the full lifecycle of small open models — registry & download, domain adaptation without retraining (soft-MoE / weight-space patching), LoRA fine-tuning, benchmarking (lm-eval-harness + custom benchmarks), RAG over your own documents, chat inference and model publishing to Hugging Face.

Stack: Django + DRF + Celery (CPU and GPU workers) + PostgreSQL + Redis + FAISS + transformers/peft/bitsandbytes. Runs comfortably on a 4 GB GPU (quantized pipelines).

Hardware reality: all heavy work (embeddings, MoE scans, fine-tuning, benchmark runs, QA generation) executes in the dedicated GPU Celery worker so the web UI stays responsive — check the GPU status page.

2. Model registry & GGUF

Import — Models → Upload: from Hugging Face (repo-id, revision, optional write-token in Profile) or a local path. Downloads run in the background (CPU worker); progress is visible on the model card and on the metrics page.

GGUF — convert any safetensors checkpoint with the pinned llama.cpp converter (Models → Convert to GGUF, q8_0 default). A GGUF checkpoint can also be imported back as a regular model — the soft-MoE scanner dequantizes it automatically.

Versions — every checkpoint keeps a version history; create a snapshot before risky operations, restore any time.

Publishing — soft-MoE experts push straight to Hugging Face from the job page (write-token required in Profile); the yellow «⭡ HF» badge on cards links to the published repo.

3. Soft-MoE / WSP experts

A domain expert is built from a dense base model without retraining: an activation scan isolates the domain direction d̂, a steer-patch (W += α·outer(d̂, ī)/‖ī‖²) is written into safetensors, and an embedding router dispatches domain prompts to the expert.

Workflow: Theme (25–30 domain prompts + contrastive set, aligned lengths) → validation gate (cross cosine < 0.5) → build job: activation scan → AUC gate (> 0.85) → steer-patch → eval gate → router. If a gate fails, the patch is not applied.

Tuning knobs: α (mix strength) and layer position (last/mean). The empirical recipe from the pilot grid: α = 0.1 + position = last gave the best code2text BLEU; RAG-corpus prompts ≈ weight-lab prompts (no measurable difference).

Interactive tools: click-to-repatch on scan charts (select layers/groups → new job reusing the parent scan, ~1 min), WSP ablation mode (goal=ablate), LLM report interpretation.

Limits: eval gate for models ≥ 2.5B on a 4 GB GPU is honestly skipped (full-GPU nf4 does not fit); 2B runs quantized on GPU. GGUF output is provided via a sibling «-GGUF» repo on HF.

4. Fine-tuning & distillation

Three trainers — instruction (LoRA on QA pairs), RAFT (retrieval-augmented: oracle chunks + distractors drawn from RAG collections via lexical-overlap ranking), document (continued LM on collection texts). Completion-only masking: loss is computed on the answer (+EOS) only.

Dataset sources — distillation datasets, manual instruction sets, Hugging Face datasets (JSONL) and RAG document collections; the selection is stored in training_config and consumed directly by the trainers.

Tier-1 LoRA pack — DoRA, rsLoRA, LoRA+ (separate lr for lora_B), NEFTune noise, target-module presets (attention / attention+mlp / hybrid-full auto-selected per model_type). Gradient checkpointing runs with use_reentrant=False (the reentrant path silently zeroes LoRA grads).

Distillation — a teacher checkpoint generates questions from RAG chunk groups, then answers them with context; the builder assembles an instruction dataset (question/answer pairs, JSONL export).

Ops — pause/resume from checkpoints, GPU device selection, live loss charts and metrics on the job page. CPU fallback explicitly rejects int4/int8 (bitsandbytes requires CUDA) — use float16 for CPU runs.

5. Benchmarks & evaluation

Standard benchmarks — lm-eval-harness 0.4.13 in an isolated venv (/opt/lmeval-venv, 14 683-task registry): install a dataset → pick a model → run → per-benchmark runs on the leaderboard. One benchmark per run (a fresh CUDA process) — combined multi-task runs OOM on 4 GB GPUs.

Custom benchmarks — generate QA pairs from any RAG collection (LLM proposes question/answer/keywords per chunk, editable), run them on any checkpoint with keyword-scoring. This is how domain effects that standard benchmarks can not see are demonstrated.

Model evaluation — multi-model × one dataset tasks, side-by-side answer comparison, ratings (the rating store also feeds future preference-based training).

HumanEval note — requires HF_ALLOW_CODE_EVAL=1 and the --confirm_run_unsafe_code flag; both are wired into the run task.

6. RAG — ingestion & search

Ingestion — collections of documents: PDF (tables + images extracted), DOCX/PPTX (tables, media), EPUB, HTML, Markdown, RTF, CSV/XLSX (tabular chunks), plain text. Chunking strategies: paragraph / semantic / fixed / recursive; per-collection chunk size and overlap; NUL-sanitized before the first save.

Indexing — embeddings via the collection's embedding model (batch 32, CUDA-OOM fallback to CPU), FAISS flat index per collection + BM25 keyword index; a document is INDEXED only when its vectors actually reached the index.

Search — hybrid: FAISS (cosine) + BM25 normalized to 0..1, freshness weighting, optional cross-encoder reranker (collection-bound or auto by language, Russian cross-encoder for ru). Reranker scores are sigmoid-squashed into the 0..1 scale.

RAG chat — one-shot query → search → generation with source attribution (top-3 chunks with per-signal scores); RAG context in the regular chat is built by the same hybrid search.

Indexes are per-collection: after heavy re-ingestion run «Build index» once; incremental «Update index» adds chunks created after the last build/update.

7. Inference, chat & comparison

Chat sessions — any checkpoint (transformers in-process or vLLM endpoint), per-session model switching, generation presets (named parameter profiles), export.

Comparison — ModelComparison objects: several checkpoints against a shared prompt list, side-by-side results.

Merging — mergekit-based model merges (linear / SLERP / TIES / DARE) with dtype auto-resolution.

Model memory — models are loaded to Redis-tracked resident slots; TTL refresh and stale-lock cleanup run as beat tasks. Resident models are shown on the metrics page even when the web container itself is CPU-only (state lives in Redis, shared with the GPU worker).

9. Troubleshooting
502 for everything after a rebuildnginx caches the web container IP once at start — after any docker compose up -d recreation run docker restart ivanna_nginx.
GPU card shows CPU-onlyCUDA is invisible to the container — check the GPU is mounted (nvidia-smi on the host, device request in compose) and restart the stack; detailed stats: /gpu-status/.
«Received unregistered task»Task code changed but the worker was not restarted — restart both workers after any tasks/*.py edit; new tasks must be present in task_routes (both config/celery.py and settings.py).
2B+ nf4 model OOM on 4 GB2B fits quantized full-GPU; ≥ 2.5B honestly skips the eval gate. Use GGUF or CPU offload paths.
GGUF does not load in llama-cpp-python 0.3.36Runtime is too old for hybrid-arch GGUF — upgrade the runtime to 0.3.37+; no re-conversion needed.
Document stuck in PROCESSINGWorker restart mid-processing leaves the guard on — press Process again (API/UI resets the stale status first).
Plotly/JS assets 404Vendored libs are served from /media/vendor (bind mount); after adding files run collectstatic for /static assets.
10. Code architecture (for developers)

The monolith modules were split into domain packages (imports stay backward-compatible through package __init__ re-exports):

ivanna_model_manager/models/core, registry, chat, evaluation, rag, search, pipelines, fine_tuning, distillation, moe, benchmarks
.../views/utils, core, registry, experiments, chat, evaluation, rag, retrieval, fine_tuning, distillation, moe, benchmarks
.../api_views/core, registry, hf, rag, chat, evaluation, fine_tuning, distillation
.../services/rag_service (hybrid search), faiss/bm25/vector_store, embedding, redis_model_service, chat_service, download, soft_moe/, fine_tuning/ (trainers + lora.py), benchmarks/
.../tasks*.pyCelery: tasks.py (models/eval/datasets), tasks_rag (ingestion), tasks_moe, tasks_benchmarks, tasks_embedding

Conventions — comments/logs in English; RU strings only inside verbose_name/help_text/_() (they are i18n msgids, EN lives in app/locale/en/LC_MESSAGES/django.po); migrations are committed to git (CI runs makemigrations --check); pinned stack: transformers 5.12.1 + accelerate 1.6.0 + bitsandbytes 0.49.2.

Repository — wiskeone/ivanna-lab on GitHub; published models under NikitaLazarev/ on Hugging Face. Deep-dive docs live in docs/ (benchmarks, soft_moe) and ROADMAP.md.
